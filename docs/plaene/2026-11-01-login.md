# Plan: Login mit Supabase

**Ziel:** Jede Seite der App ist nur nach der Anmeldung mit E-Mail und Passwort erreichbar, und die Anmeldung hält bis
„Abmelden“.

**Vorgehen:** Der Browser spricht nie selbst mit Supabase. `proxy.ts` prüft und erneuert die Sitzung vor jeder Anfrage,
An- und Abmelden laufen als Server Actions. Die Cookies setzt also immer der Server, sie können `HttpOnly` sein, und die
7-Tage-Grenze von Safari für Cookies aus JavaScript greift nicht. Ein Assistent führt danach durch die Einrichtung bei
Supabase und Vercel.

**Technik:** `@supabase/ssr` 0.12.7, `@supabase/supabase-js` 2.118.0, Next.js 16 (`proxy.ts`, Server Actions,
`useActionState`), Vitest mit Attrappe für Supabase.

**Anforderung:** [[projects/tages-dashboard/docs/Projektvision|Projektvision]], Fahrplan Phase 1, Schritt 2, und die
Befragung vom 2026-10-25.

## Gratis-Grenzen, nachgelesen am 2026-11-01

Quellen: [Pricing](https://supabase.com/pricing), [Rate Limits](https://supabase.com/docs/guides/auth/rate-limits),
[Project Pausing](https://supabase.com/docs/guides/platform/free-project-pausing),
[Sessions](https://supabase.com/docs/guides/auth/sessions).

- **Tarif Free:** 2 aktive Projekte, 50.000 Nutzer im Monat, 500 MB Datenbank, 5 GB Datenverkehr. Reicht für einen Nutzer.
- **Mailversand:** 2 Mails pro Stunde im ganzen Projekt. Trifft uns nicht: Passwort-Anmeldung, Nutzer ohne Bestätigungsmail.
- **Anmeldeversuche:** 150 Anfragen an `/auth/v1/token` in 5 Minuten je IP-Adresse, darüber Fehler 429.
- **Sitzung:** läuft im Tarif Free nie von selbst ab. Refresh Tokens gelten unbegrenzt, jedes nur einmal.
- **Pause:** nach 1 Woche mit zu wenig Datenbank-Aktivität. **Offen:** Die Doku sagt nicht, ob Login-Anfragen zählen,
  und das Projekt hat vor Phase 4 keine eigenen Tabellen. „Bei täglicher Nutzung kein Problem“ aus der Befragung ist
  also unbelegt. Vorgehen: beobachten (Aufgabe 6, Schritt 5), erst bei einer echten Pause etwas bauen.

## Feste Vorgaben

- Branch `feature/login`, ein PR für Plan, Code und Doku. Vor dem Merge `/code-review`.
- Ein Supabase-Projekt online, Tarif Free, keine lokale Supabase. Der lokale Server meldet sich dort an.
- Registrierung aus, der einzige Nutzer entsteht im Supabase-Dashboard.
- Variablen: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Der Secret Key wird nicht gebraucht.
- Kein Browser-Client von Supabase (`createBrowserClient`).
- Sitzung auf dem Server nur mit `getClaims()` prüfen, nie mit `getSession()`: Dessen Ergebnis ist ungeprüft und fälschbar.
- Nur `proxy.ts` erneuert die Sitzung, sonst drohen zufällige Abmeldungen durch doppelt benutzte Refresh Tokens.
- Keine Weiche „ohne Variablen Prüfung überspringen“ wie im Next.js-Beispiel: Fehlende Variablen führen zu Fehler 500,
  nie zu einer offenen Seite.
- Seiten lesen beim Rendern keine Cookies, sonst verlangt `cacheComponents` eine `<Suspense>`-Grenze.
- Versionen der beiden Pakete fest eintragen (`npm install --save-exact`).
- Tests ersetzen Supabase durch eine Attrappe, kein Test ruft Supabase wirklich auf.
- Vor jedem Commit `npm run check`. Commit-Nachrichten englisch, im Imperativ, mit Co-Authored-By-Zeile.
- Texte in der Oberfläche auf Deutsch.

## Prüf-Schwerpunkte

1. Falsches Passwort → Meldung „E-Mail oder Passwort stimmt nicht.“, keine Weiterleitung → Aufgabe 3, Test 2.
2. Supabase pausiert oder nicht erreichbar → „Anmeldung gerade nicht möglich.“, nicht „Passwort falsch“ → Aufgabe 3, Test 3.
3. Sitzung wird beim Prüfen erneuert oder gelöscht und zugleich weitergeleitet: Die Cookies müssen auch auf der
   Weiterleitung landen, sonst fliegt man später heraus → Aufgabe 2, Test 5.
4. Variablen fehlen bei Vercel → Fehler statt offener Seite → Aufgabe 2, Test 6.
5. Neue Seite oder Schnittstelle ohne eigenen Schutz, ähnlich benannter Pfad wie `/login-alt` → Weiterleitung auf
   `/login` → Aufgabe 2, Test 1 und 2.
